# 🍺 Beer Geek Madness Bot

Telegram бот для розпізнавання пива на фото та пошуку на Untappd.

## Як це працює

1. Користувач надсилає фото таблички з назвами пива
2. Claude Vision API розпізнає рукописний текст
3. Бот шукає пиво у локальній базі (fuzzy matching)
4. Якщо не знайдено — генерує посилання для пошуку в Google/Untappd
5. Повертає прямі посилання на `untappd.com/beer/{id}`

## Фестивальний чекін (Telegram Mini App)

Команда `/checkin` відкриває вбудований у Telegram Mini App для швидких чекінів
на фестивалі: пошук пива → вибір → оцінка (0–5 з кроком 0.25) → екран
підтвердження → реальний чекін на Untappd.

Працює через сторонній Untappd MCP-сервер (`untappd_mcp.py`). Веб-сервер
(`webapp_server.py`, aiohttp) стартує в тому ж процесі, що й бот, і слухає той
самий порт 8080, який Fly.io вже очікує (`fly.toml`). Кожен API-запит
перевіряється через підпис Telegram `initData` (HMAC), тому доступ ззовні без
реального запуску з Telegram неможливий.

Навігація "назад" підключена до нативного `Telegram.WebApp.BackButton` —
на Android він перехоплює системну кнопку/жест "назад" (інакше вона просто
згортає весь Mini App замість переходу на попередній екран); на iOS/desktop
показує стрілку в шапці. Реалізовано без дублювання логіки "куди назад" —
клік по BackButton просто симулює клік по вже наявній кнопці поточного
екрана (`[data-back]` або `#rate-back-btn`).

**Мультикористувацько**: кожен друг підключає **власний** Untappd-акаунт
командою `/connect_untappd` (приватно, вставляє свій особистий токен) —
`user_tokens.py` зберігає токени по Telegram user id у `DATA_DIR`, і кожен
чекін іде саме з токена того, хто його зробив, а не власника бота. Якщо
змінна `OWNER_TELEGRAM_ID` виставлена — власник бота може продовжувати
користуватись без `/connect_untappd`, підхоплюючи `UNTAPPD_MCP_TOKEN` як
фолбек лише для свого Telegram id.

**Спільна черга** (`checkin_queue.py`): будь-хто в групі може додати пиво в
чергу кнопкою "+" у пошуку — усі бачать однаковий пронумерований список
("хто приніс що"), розв'язує плутанину "яке пиво в якому келиху" на великих
дегустаціях. Черга не зберігає "відмічено/ні" сама по собі — статус "уже пив"
запитується напряму в Untappd окремо для кожного, хто дивиться.

Зникнення пункту з черги — завжди **особисте**, для кожного окремо: після
реального чекіну через чергу (`completedBy`) або натискання ✕ (`hiddenBy`).
Пункт лишається в спільній черзі для всіх інших, доки вони самі не зачекінять
або не приберуть його — так один учасник не може випадково прибрати щось із
черги в тих, хто ще не встиг це спробувати.

Кнопка "🗑 Очистити все" на екрані черги (`checkin_queue.hide_all`) — той самий
особистий механізм `hiddenBy`, застосований одразу до всіх поточних пунктів:
чистить чергу лише в перегляді того, хто натиснув, іншим нічого не зникає.
Потрібна тому, що перемикання на JSON іншого фестивалю (`FESTIVAL_BEERS_FILE`,
див. розділ "Встанови змінні оточення") саме по собі чергу не очищує —
застарілі пункти просто стають нерелевантними, а не видаляються, і ця кнопка
дає спосіб прибрати їх вручну.

**Прогрес фестивалю** (вкладка "📊 Прогрес"): скільки пива з фестивального
списку **особисто ти** вже спробував — загалом і по кожній сесії
(жовта/синя/червона/зелена). Персональний, як і бейдж "✅ вже пив" у
пошуку — побудований на тому самому `had_it_index.py` (без жодних
живих запитів до Untappd per beer: із ~824 пив на всіх сесіях це б
миттєво спалило спільну квоту, тож рахунок іде виключно по вже
синхронізованому фоновому індексу). Без підключеного Untappd-акаунта
особистої історії просто нема, тож усе показує як "ще не спробував" —
той самий деградейшн, що й у бейджа "вже пив" в пошуку.

Тап на сесію в "Прогресі" відкриває повний список пива цієї сесії з
пошуком зверху (`/api/checkin/festival/session`) — ще не спробуване (або
невідоме — фонова індексація ще не дійшла) показується першим, уже
спробуване — внизу, приглушене. Одне й те саме пиво, наявне в кількох
сесіях одночасно, рахується спробуваним у **кожній** з них щойно
зачекинене хоч раз — сесія тут лише мітка на тому самому `beerId`, не
окрема сутність.

**Сесії не прив'язані до конкретних назв кольорів.** Реальна ідентичність
сесії — завжди її сирий ключ із вхідного JSON (`"friday"`/`"saturday"`,
`"yellow"`/`"blue"`, будь-що інше), і саме він фігурує в `_session_order`.
Колір (yellow/blue/red/green) — суто косметичне позначення для крапки/емодзі
в інтерфейсі: `_assign_session_colors` (`webapp_server.py`) мапить кожен
ключ на один із 4 кольорів у порядку появи (назва, що вже збігається з
кольором, лишається без змін), і при 5+ сесіях колір просто повторюється —
це ніколи не зливає дві різні сесії в один блок статистики, бо рахунок і
фільтрація завжди йдуть по реальному ключу, а не по кольору. "Прогрес"
показує лише сесії, що реально є у файлі (раніше через мапінг "лише на 4
кольори" фестиваль з 2 сесіями (`friday`/`saturday`) показував ще 2 порожні
"Червона"/"Зелена" — цей баг був у самому дизайні, не в конкретних даних).
Файл без сесій (плаский список пива) так само коректно отримує один
синтетичний блок замість того, щоб уся фіча прогресу мовчки показувала 0/0.

**Пам'ять локації**: після чекіну з вказаною локацією вона зберігається в
`user_tokens.json` (`last_venue`, персонально для кожного) і підставляється
автоматично на наступному чекіні — на фестивалі локація майже завжди та сама
весь день, тож нема сенсу обирати її щоразу заново. Кнопка "📍 Додати
локацію" лишається доступною, щоб змінити її вручну. Окремого поля "purchase
location" в `check_in` не існує — сама подія чекіну прив'язується лише до
однієї локації (`foursquareId`+`geolat`+`geolng`), без окремого місця
покупки.

**Локації поруч + "лише нові"** (`foursquare.py`, `venue_index.py`): Untappd
сам не має пошуку локацій ("Untappd has no venue search" — так і написано в
описі `get_my_recent_venues`), тому кнопка "🧭 Локації поруч" шукає напряму
через **Foursquare Places API** (`https://places-api.foursquare.com`,
власний `FOURSQUARE_API_KEY`, окремий від Untappd-квоти сервіс і кошт
користувача). ID венью з Foursquare (`fsq_place_id`) підтверджено напряму —
той самий 24-символьний ID, що й `foursquareId`, який приймає Untappd
`check_in`, тож результат пошуку йде туди без додаткового мапінгу.
Чекбокс "лише нові" ховає локації, де користувач вже точно був — це
вимагає окремого повного фонового індексу відвіданих локацій
(`venue_index.py`, той самий tri-state/round-robin підхід, що й
`had_it_index.py`, але побудований через `get_user_checkins` — пагінація за
`checkin_id`, бо в цього методу нема `total_count`); локація ховається
лише при **підтвердженому** "так, був" — невідомий статус ніколи не ховає,
щоб не пропустити справді нове місце під час незавершеного першого проходу
індексації. Чекбокс "🏅 Лише для бейджа" фільтрує локації до тих, чия Foursquare-категорія
(або будь-яка з субкатегорій) реально дає прогрес до одного з venue-бейджів
Untappd — звірка йде проти `badge_venue_categories.json` (зібраний вручну
цього сеансу з публічного каталогу `badges.untappd.com`, не через API/квоту).
Локації, що пройшли фільтр, показують, який саме бейдж вони дають, разом із
реальною мініатюрою бейджа (`matchedBadges`, кожен елемент `{name, icon}` —
`icon` це пряме посилання на `assets.untappd.com`, зібране одночасно з
категоріями з того ж каталогу). Файл — статичний довідник у репозиторії,
вантажиться одноразово при старті сервера.

Геолокація береться через Telegram Mini App `LocationManager`
(Bot API 8.0+; на десктопному Telegram чи старих клієнтах може бути
недоступна — тоді лишається лише список "Мої локації"). Є й текстовий
пошук локації за назвою (Foursquare `query`, працює навіть без геолокації —
Foursquare тоді сам підбирає широкий регіон; якщо перед цим вже
використовували "Локації поруч", координати підхоплюються автоматично для
кращої релевантності). Радіус пошуку за назвою за замовчуванням — 100км (не 500м, як для "поруч") —
це реальний максимум, який приймає Foursquare API (перевірено: 100000
працює, 200000 повертає 400 Bad Request). Інакше реальні збіги за кілька км
губились серед ближчих, але нерелевантних текстових збігів (перевірено на
реальному прикладі: пошук "Zoo" з вузьким радіусом пропускав сам зоопарк за
2.9км, лишаючи тільки зоомагазини поруч).

Обидва чекбокси ("лише нові"/"лише для бейджа") при перемиканні
автоматично перезапускають останній пошук (nearby або за текстом) — без
цього список просто лишався застарілим до наступного нового запиту.

**Фільтри пошуку пива** (два чекбокси над результатами на головному екрані):
"Фестивальний список" (за замовчуванням увімкнено) піднімає збіги з
локальної бази фестивалю на початок видачі; "Вішліст" піднімає збіги з
вішліста одразу після — обидва чекбокси незалежні один від одного (можна
увімкнути лише вішліст, і його збіги підуть першими). Обидва чекбокси
**не обмежують** видачу — це лише порядок: живий пошук по всьому каталогу
Untappd (`search_beers`, безкоштовний) завжди довантажує решту місць
після локальних збігів, а якщо жоден чекбокс не увімкнено —
видача чисто за звичайною релевантністю, без жодного пріоритету.

**Обмеження Untappd API**: пошук (`search_beers`) безкоштовний, а сам чекін
(`check_in`) витрачає квоту — 100 запитів/годину **на токен**, підтверджено
живим запитом двох різних підключених акаунтів одночасно (`remaining` у них
відрізнявся — 32 і 68 в один момент часу). Раніше (на початку цього сеансу)
`get_untappd_api_usage`'s власний `note` прямо стверджував, що квота
**спільна** на весь MCP-сервер, "per Untappd app key" — і живі виміри це
підтверджували (усі підключені бачили однакове число). MCP-сервер, схоже,
згодом це полагодив на своєму боці: `note` тепер каже "rate-limits
authenticated calls **per access token**", і числа в різних користувачів
дійсно різні. Код (`_quota_allows` та всі виклики `get_untappd_api_usage`)
з самого початку читав `remaining` за токеном **того ж користувача**, чию
дію перевіряв, тож ця зміна на боці сервера підхопилась без жодної правки
коду — просто фонові цикли різних людей більше не заважають одне одному.
Немає можливості видалити/редагувати чекін заднім числом, тому екран
підтвердження — єдиний запобіжник від помилки.

Кожен рядок пива (пошук, черга, список сесії) має кнопку "🔗" — пряме
посилання на `untappd.com/beer/{id}` через `Telegram.WebApp.openLink`.
Це не витрачає нашу квоту взагалі (той самий реальний застосунок/сайт
Untappd, у обхід MCP) — корисно як запасний варіант, коли своя квота на
нулі або сам чекін через застосунок з якоїсь причини не працює.

**Фонова індексація "вже пив"** (`had_it_index.py`): пряма перевірка кожного
пива при пошуку (`check_i_had_beer`) швидко з'їдає спільну квоту — тож
реальна перевірка обмежена першими 5 результатами пошуку. Щоб бейдж "✅ вже
пив" покривав **усю** історію чекінів (не лише недавні), окремий фоновий
цикл повільно (за замовчуванням ~1 сторінка/30с, лише якщо лишається
запас квоти понад `HAD_IT_BACKFILL_MIN_REMAINING`) обходить повну історію
чекінів кожного підключеного користувача через `get_user_beers` і зберігає
результат у `had_it_index.json`. Дата-фільтр цього ж методу (`startDate`/
`endDate`) виявився ненадійним (сортує/фільтрує, схоже, за датою **першого**
знайомства з пивом, а не останнього чекіну) — тому обхід іде без фільтра
дат, просто по сторінках від початку до кінця. Після завершення першого
повного проходу бейдж "не пив" стає **впевненим** (а не просто "ще не
перевірено"); повторний прохід запускається раз на добу
(`HAD_IT_BACKFILL_RESYNC_COOLDOWN_SECONDS`), щоб підхопити чекіни, зроблені
напряму через застосунок Untappd.

**Стиль/пивоварня/країна пива тепер теж зберігаються** (`record_page`) —
для локального підрахунку прогресу бейджів (наприклад, скільки країн уже
випито) не знадобився жоден новий запит: ці поля вже були в тій самій
відповіді `get_user_beers`, за яку й так платили квотою заради `rating`, —
просто раніше відкидались. Зважений на це: `get_beer(beerId)` окремо на
кожне з ~30 тис. унікальних пив коштував би реально дорого — а так дані
підтягнуться самі, поступово, за один звичайний плановий ресинк (до 24
год), без жодної додаткової витрати квоти понад те, що й так вже
витрачається на підтримку бейджа "вже пив". Старі записи, зроблені до
цього фіксу, просто не мають цих полів, доки їх не торкнеться черговий
ресинк — це не помилка, а очікуваний перехідний стан.

Перевірка "чи лишилось достатньо квоти" (`_quota_allows`) враховує **вік**
показника `remaining`, не лише саме число — `get_untappd_api_usage` сам
нічого не витрачає й нічого не оновлює, тож `remaining` застигає, якщо цей
самий токен (тепер, коли квота per-token, а не спільна — саме "цей самий",
не будь-хто інший) довго не робив реальних запитів. Без цього застарілий
"мало" міг би заблокувати фоновий цикл **назавжди**: цикл ніколи не зробить
перший реальний запит, який оновив би дані, бо завжди бачить те саме старе
низьке число (реально спостережений і виправлений дедлок цього сеансу).
Поріг "довіряти застарілості" (`QUOTA_STALENESS_SECONDS`) — спочатку було
повне rolling-вікно (3600с/60хв, "гарантовано застаріле"), але це виявилось
задовгим на практиці: живими даними двічі зафіксовано майже-дедлок — читання
на кшталт `remaining=19, ageSeconds=3411` блокує всі три фонові процеси
(had-it/venue/auto-тост) одночасно ще майже 200 секунд, хоча воно вже
очевидно застаріле (за годину активний акаунт точно встиг би щось
зачекінити). Знижено до третини вікна — 1200с/20хв — досить старе, щоб
значна частина запитів позаду вже випала з rolling-години, але не настільки
коротке, щоб реагувати на кожну коротку паузу активності.

**`/import_history`** — швидший шлях для Untappd Insider (платна підписка):
офіційна функція "Export Your Data" видає CSV/JSON з **усією** історією
чекінів одним файлом (поля підтверджено: `bid`, `rating_score` тощо).
Завантаж цей файл боту приватно після `/import_history` — `had_it_index`
наповнюється миттєво й позначається `fully_synced`, **без жодного запиту**
до Untappd API, і повільний фоновий обхід для цього користувача більше не
потрібен (`had_it_index.seed_from_export`). Формат JSON-експорту не
перевірявся на реальному файлі цього сеансу (лише колонки CSV підтверджено
живим пошуком) — парсер обробляє і "голий список", і `{"checkins": [...]}`,
але про всяк випадок деградує до "0 імпортовано" замість падіння, якщо
структура виявиться іншою.

**`/auto_toast`** (`auto_toast.py`) — автоматично тостить нові чекіни обраних
Untappd-юзернеймів, використовуючи нові MCP-інструменти `toast_checkin`/
`comment_checkin` (з'явились на сервері у вересні 2026). Внутрішньо
персонально (кожен власник керує власним списком і виключеннями, один на
одного не впливають) — але поки що це особиста тестова фіча: доступна
лише одному Telegram `user_id` (`AUTO_TOAST_OWNER_ID`, env-конфігурований,
за замовчуванням — власник бота). Обмеження діє на трьох рівнях: команда
`/auto_toast` одразу відповідає "недоступно" для решти, її взагалі немає
в меню команд інших приватних чатів (`BotCommandScopeChat` лише для
власника замість `BotCommandScopeAllPrivateChats`), а таб "🍻 Авто-тост"
і перемикач у "⚙️ Налаштування" самі ховаються в Mini App (`isAutoToastOwner`
з `/api/checkin/usage`) — і всі API-роути фічі так само перевіряють це
на бекенді, а не покладаються тільки на приховану кнопку. Команди:
```
/auto_toast                       - показати статус (кого тостимо, скільки тостнуто востаннє)
/auto_toast add <юзернейм> ...    - додати одного чи кількох
/auto_toast remove <юзернейм>     - прибрати
/auto_toast exclude <країна>      - не тостити чекіни з цієї країни (розпізнає "рф"/"росія"/"russia" й "білорусь"/"беларусь"/"belarus" як один запис; будь-що інше зберігається як є)
/auto_toast include <країна>      - зняти виключення
/auto_toast pause                 - тимчасово вимкнути (наприклад, на час фестивалю, щоб зберегти квоту для реальних чекінів)
/auto_toast resume                - увімкнути назад
/auto_toast legacy_only           - тостити лише "Legacy Drinks" (пропускати Non-Alcoholic/RTD/Spirit/Wine) - увімкнено за замовчуванням
/auto_toast all_categories        - тостити взагалі все, включно з Non-Alcoholic/RTD/Spirit/Wine
```
Пауза (`enabled: false` в `auto_toast.json`) не чіпає список цілей і статистику
— просто пари цього власника повністю випадають з ротації `_auto_toast_loop`,
не сповільнюючи нікого іншого.

**`legacyOnly` (типово `true`).** Untappd сам ділить усі стилі на "Legacy
Drinks" (пиво/сидр/мед/hard kombucha/malt-based seltzers/hard root beer
і т.п., завжди увімкнено) і 6 новіших нетрадиційних категорій (оновлення
листопада 2025 "expands beyond beer", усі вимкнені за замовчуванням) —
**Non-Alcoholic, Ready-to-Drink, Sake, Spirit, THC-based Drink, Wine**.
Джерело — власний екран "Filter by Style" в налаштуваннях застосунку
Untappd (заскріншотено вживу цього сеансу), точний текст:

> Non-Alcoholic — Packaged drinks like sodas, juices, waters, mocktails,
> and functional beverages that may contain CBD. **This setting does not
> include non-alcoholic versions of legacy drinks.**

Це останнє речення важливе, але **не блокове правило** — не "кожен
`Non-Alcoholic - X` лишається Legacy", а розподіл **по кожному
підстилю окремо**. Пройшли через дві хибні версії, перш ніж дійшли до
точного списку:

1. Спочатку `"non-alcoholic"` був у `_NON_LEGACY_PREFIXES` (за аналогією
   з RTD/Spirit/Wine) — і це реально зупинило тост для BrewDog "Nanny
   State" (стиль `"Non-Alcoholic - Pale Ale"`), хоча це пиво.
2. Прибрали `"non-alcoholic"` з префіксів повністю — але це теж
   неправильно: користувач показав живий скрін розгорнутої категорії
   "Non-Alcoholic" у налаштуваннях застосунку з конкретними підстилями
   всередині (`Fassbrause`, `Kombucha`, `Malt Soda`, `Malta`) — вони
   справді НЕ Legacy, а самостійні напої, помилково не виключені.
3. Користувач нарешті надав **повний HTML `<select>`** зі style-піквера
   Untappd — усі 36 варіантів `"Non-Alcoholic - X"` з реальними
   числовими `style_id`. ID показують чіткий патерн: **33, 358–366** —
   оригінальні id (до оновлення) — усі 17 справжні пивні/сидрові/медові
   підстилі (Bitter, Blonde/Golden Ale, Brown Ale, Cider/Perry,
   Farmhouse Ale, Festbier/Märzen, Fruit Beer, IPA, Lager, Mead, Other
   Beer, Pale Ale, Porter/Stout, Red Ale, Shandy/Radler, Sour, Wheat) —
   **Legacy**. **999–1016** — перша партія нових id (CBD Beverage,
   Coffee, Energy Drink, Fassbrause, Functional Beverage, Hop Water,
   Kombucha, Malt Energy Drink, Malt Soda, Malta, RTD Cocktail,
   Shrub/Drinking Vinegar, Soda - Craft, Soda - Mass Market, Sparkling
   Water, Spirit Alternative, Tea/Lemonade, Wine) — жодне не пиво —
   **не Legacy**. **1255–1264** — друга, пізніша партія нових id, але
   цього разу здебільшого ЩЕ пивні стилі (Fruit Beer, Blonde/Golden Ale,
   Brown Ale, Festbier/Märzen, Bitter, Red Ale, Farmhouse Ale — Legacy,
   попри "новий" id), крім `"Non-Alcoholic - Other"` (id 1264, без слова
   "Beer" — на відміну від `"...- Other Beer"` id 33, яке точно Legacy)
   — підтверджено користувачем як **не Legacy**.

Фінальний список — явний набір `_NON_LEGACY_STYLES` (19 конкретних
рядків), а не спроба вивести правило з префікса. `_NON_LEGACY_PREFIXES`
(`{"rtd", "sake", "spirit", "thc", "wine"}`) лишається окремо для
категорій, де підрядковий префікс дійсно надійний (`"RTD -
Margarita"`, `"Sake - Junmai"`, `"Spirit - Vodka"`, `"THC - ..."`,
`"Wine - Riesling"`) — на відміну від `"Non-Alcoholic"`, який Untappd
використав для двох різних речей одразу. Якщо колись з'явиться ще не
внесений у список `"Non-Alcoholic - X"` варіант, він пройде як
"legacy" за замовчуванням (та сама неагресивна поведінка, що й для
чекіну без стилю взагалі) — до підтвердження.

Чекін без стилю трактується як "legacy" (нема на чому судити — та сама
конвенція, що й в `is_country_excluded` для відсутнього
`venue_country`). Перевірка йде в `_auto_toast_loop` поряд з
`auth_toast`/country-виключенням — до виклику `toast_checkin`, тож
нетостовані чекіни цих категорій просто ніколи не торкаються Untappd
API, без жодної зайвої витрати квоти.

**Чи може auto-тост зняти вже поставлений вручну тост?** Ні — `toast_checkin`
насправді тогл (додає тост, якщо його нема, і **знімає**, якщо вже є), але
цикл щоразу свіжо перевіряє `toasts.auth_toast` із самої відповіді API
**перед** викликом і просто пропускає чекін, якщо тост уже стоїть (рядок
"already toasted (e.g. manually, or a prior tick)") — тому `toast_checkin`
для вже тостованого чекіна взагалі не викликається, і випадково зняти
власний тост неможливо.

**Візуальний інтерфейс** — вкладка "🍻 Авто-тост" у тому самому Mini App
(`/checkin`), поруч із "🥤 Черга"/"📊 Прогрес". Перемикач вгорі — те саме
`pause`/`resume`, що й команда; нижче — повний список Untappd-друзів
(`get_user_friends`, кешується на годину — повний список важкого акаунта
займає ~10 запитів, тож не варто тягнути його щоразу) з чекбоксами й
пошуком. Кожен клік по чекбоксу одразу зберігає **весь** позначений набір
(`/api/checkin/autotoast/set_targets` → `auto_toast.set_targets`) — без
окремої кнопки "зберегти", як і решта інтерактивних елементів цього
застосунку. Ціль, яку раніше додали командою `/auto_toast add`, але яка не
є взаємним другом на Untappd (чи просто випала з кешованої сторінки),
однаково показується позначеною — інтерфейс ніколи не "губить" активну
ціль мовчки. Зняття галочки видаляє прогрес (`last_checkin_id`,
накопичену статистику) для цієї цілі — повторне позначення почне з чистого
bootstrap, як і для щойно доданої людини.

Фоновий цикл (`webapp_server.py`'s `_auto_toast_loop`, окремий споживач
спільної квоти, як і два бекфіли вище) раз на ~60с обходить усі пари
"власник → ціль" по черзі й тостить усе нове, крім: уже тоснутого
(`toasts.auth_toast`) і чекінів, чия `venue.location.venue_country`
збігається з виключеною країною (чекін без локації — без локації нема з
чим звіряти, тостимо як завжди). **Перший** обхід щойно доданої цілі нічого
не тостить — лише запам'ятовує поточний найновіший чекін як точку відліку,
щоб додавання людини з роками історії не тоснуло все одразу пачкою.

**Два реальні баги знайдено й виправлено живим тестуванням одразу після
першого запуску** (симптом: у списку були люди з новими чекінами, а тости
не з'являлись):

1. `get_user_checkins` із параметром `minId` повертає **іншу форму
   відповіді**, ніж без нього — не вкладену під `"checkins"`, а прямо
   `{"count", "items", "pagination"}` на верхньому рівні. Код усюди читав
   лише вкладену форму, тож `minId`-запит мовчки виглядав як "нічого
   нового", хоча насправді нові чекіни там були. Виправлено нормалізацією
   форми відповіді один раз усередині `untappd_mcp.get_user_checkins`, аби
   жоден виклик коду більше не мусив про це знати.
2. Навіть після виправлення форми відповіді, `minId`-запит **сам по собі**
   непридатний для "наздоганяння" великого напливу: він завжди повертає
   лише 25 найновіших елементів (стеля цього MCP-інструмента), і немає
   способу попросити "наступну партію" — якщо в цілі назбиралось понад 25
   нових чекінів між тіками (наприклад, масовий імпорт історії), курсор
   стрибнув би одразу на найновіший і **назавжди** пропустив би все
   поміж. Тому опитування тепер іде назад через `maxId` (як і венью-бекфіл
   вище) — при переповненій сторінці зберігається проміжний курсор
   `catchup_max_id` і обхід продовжується на наступних тіках, доки не
   дійде до відомої межі `last_checkin_id`; лише тоді межа реально
   посувається. Перевірено симуляцією: пачка з 60 нових чекінів коректно
   розбирається за 3 тіки (25+25+10), кожен тоститься рівно один раз.

Якщо `toast_checkin` впаде на 429 (rate limit) посеред сторінки — жоден
курсор не просувається взагалі: `maxId`/`last_checkin_id` — це пороги, а не
список "що вже бачили", тож будь-яке просування вище зламаного чекіна
назавжди сховало б і його, і все старше з майбутніх запитів. Наступний тік
перезапитує ту саму сторінку — це безпечно, бо перед кожним тостом
перевіряється свіжий `toasts.auth_toast` з API, тож уже успішно тоснуте не
тоститься вдруге (що інакше зняло б тост, бо `toast_checkin` — це
перемикач).

**Черга опитування — чесний round-robin, не випадковий.** Спочатку
`next_turn()` завжди просувала чергу на наступну пару, навіть коли тік
пропускався через брак квоти на токені. При 77+ цілях на одному токені
(конкуренція з had-it/venue бекфілами й самим тостингом) це на практиці
означало: хто саме отримає реальний опит у вікні вільної квоти — залежить
від того, чия позиція в черзі якраз збіглася з цим моментом, а не хто
довше за всіх чекає. Живими даними зафіксовано розкид від 6 хв до **704
хв** між опитуваннями різних цілей одного власника. Виправлено розділенням
на `peek_turn()` (дивиться на наступну пару, не забираючи її з черги) і
`advance_turn()` (реально просуває) — цикл тепер "тримається" на одній і
тій самій парі, доки її реально не вдасться опитати (`_quota_allows`
дозволяє), і лише тоді йде далі. Просування завжди відбувається одразу
після реальної спроби опитати пару — незалежно від результату (rate limit,
успіх, чи просто "нема токена") — так пара не "застряє" в черзі назавжди
через один невдалий тік, і водночас не втрачає своє місце просто тому, що
глобально не вистачало квоти.

**Друга дірка в тій самій черзі, знайдена після додавання UI з чекбоксами.**
`peek_turn`/`advance_turn` спочатку трекали позицію як звичайний числовий
індекс (`_rotation_idx`) у списку пар. Екран "🍻 Авто-тост" викликає
`set_targets` (повна заміна списку цілей) при **кожному** кліку по
чекбоксу — а це означає список цілей може змінити порядок чи розмір у будь-
який момент. Числовий індекс після такого просто вказує на когось іншого:
пара, чия черга щойно підійшла, може безслідно "загубитись" на дуже довгий
час, поки індекс блукає по перетасованому списку. Живими даними зафіксовано
конкретний випадок: у друга з'явились нові, нічим не виключені чекіни, а
курсор для нього не зрушив з місця понад 7 годин. Виправлено переходом на
ідентифікатор-базоване відстеження (`_last_served: (owner_id, username)`
замість `_rotation_idx: int`) — наступна пара шукається як "той, хто йде
одразу після останньої обслуженої пари за іменем", а не за позицією; якщо
останню обслужену пару взагалі прибрали (зняли чекбокс), чергу просто
починає з початку, без падіння. Це стійке до реордеру й зміни розміру
списку в будь-який момент.

**Перехід на `get_my_friend_feed` — заміна архітектури опитування.** Увесь
попередній опис вище (per-target ротація по 75+ парах, `peek_turn`/
`advance_turn`, `catchup_max_id` на кожну ціль окремо) описує дизайн,
який існував, доки MCP-сервер не підтримував спільну стрічку друзів — лише
`get_user_checkins(username)` по одному за раз. Ми надіслали запит на
фічу мейнтейнеру MCP-сервера (обгортку над реальним Untappd-ендпоінтом
`GET /v4/checkin/recent` — домашня стрічка активності **всіх** друзів
одразу), і його додали як інструмент `get_my_friend_feed`. Перевірено
живими запитами: на відміну від `get_user_checkins`, тут форма відповіді
стабільна незалежно від `minId`/`maxId`, і `minId` дійсно фільтрує (а не
завжди повертає лише найновіші N, як було в `get_user_checkins`).

Це дозволило спростити архітектуру кардинально:
- **Опитування тепер per-owner, не per-target.** Один виклик
  `get_my_friend_feed` повертає нові чекіни **всіх** друзів одразу; код
  локально фільтрує лише тих, хто в списку авто-тосту (`config.targets`,
  без урахування регістру). Замість 75 запитів на оберт черги — **1** (плюс
  по одному `toast_checkin` на кожен реально новий чекін, як і раніше).
- Курсор (`last_checkin_id`/`catchup_max_id`/`catchup_target_id`) тепер
  один **спільний** на весь feed власника, а не по одному на кожну ціль —
  уся проблема нерівномірної ротації й "загублених у черзі" цілей (обидва
  баги вище) просто **зникає структурно**: нема більше 75 окремих позицій,
  які можна переплутати чи забути.
- Формат зберігання (`auto_toast.json`) мігрує автоматично й прозоро при
  першому зверненні: стара форма (`state[username] = {last_checkin_id,
  catchup_max_id, total_toasted, ...}`) перетворюється на нову
  (`feed = {last_checkin_id, catchup_max_id, catchup_target_id}` спільний +
  `stats[username] = {total_toasted}` окремо на статистику). Курсори НЕ
  переносяться (нема одного правильного спільного значення з кількох
  незалежних старих) — feed просто починає новий bootstrap, за тим самим
  правилом "не тостити заднім числом"; накопичена статистика тостів
  переноситься без втрат. Перевірено на реальній копії продакшн-файлу (75
  цілей, `esodin`/`Delacrua` та інші зберегли лічильники).
- `/auto_toast` статус тепер показує один спільний рядок "Стрічка:
  перевірено N хв тому" замість окремого "перевірено X хв тому" на кожного
  друга (бо опитування дійсно спільне) — і далі список `юзернейм — всього
  тостнуто N` для кожної цілі.

**`/festival_watch`** (`festival_watch.py`) — окрема персональна фіча,
побудована на тому самому `get_my_friend_feed`, який уже опитується для
auto-тосту, тож **без жодної додаткової витрати квоти**. На відміну від
auto-тосту (питання "чи я це вже пив" — персональне, `had_it_index`), тут
питання геть інше: "чи це взагалі є в базі фестивалю" — незалежно від того,
чи сам власник колись пив цей сорт. Ідея: якщо пивоварня на фестивалі
поміняла кран або наливає лімітку, якої нема в `mbcc_beers.json`, і хтось
із друзів це зачекінив **поруч із фестивалем** — прийде сповіщення в бот.
Працює по **всій** стрічці друзів, а не лише по списку auto-тосту (сенс —
помітити фізичну зміну на місці, а не стежити за конкретними людьми) —
і не вимагає підключеного Untappd-акаунта самого власника (лише читає вже
завантажену спільну стрічку, сама нічого в Untappd не викликає).

Керувати можна двома способами — обидва пишуть у той самий
`festival_watch.json`, тож зміна з одного інтерфейсу одразу видно в іншому:

- **Команди бота:**
  ```
  /festival_watch                - показати статус
  /festival_watch here           - встановити точку стеження за поточною Telegram-локацією (нативний location-picker)
  /festival_watch radius <метри> - радіус (за замовчуванням 500м)
  /festival_watch on / off       - увімкнути/вимкнути
  ```
  Локація тут — через стандартний Telegram-обмін геолокацією (кнопка
  "📍 Надіслати локацію"), не через `LocationManager`/Mini App.
- **Вкладка "🆕 Новинки" в Mini App** (`/checkin`, поруч із "Черга"/
  "Авто-тост") — той самий перемикач і радіус, плюс два способи задати
  точку: кнопка "🧭 Встановити мою поточну локацію" (той самий
  `ensureLocationManager()`, що й "Локації поруч") або пошук за назвою
  (перевикористовує вже наявний Foursquare-пошук локацій, `/api/checkin/
  venues/nearby`) — зручно, якщо точку треба виставити не по факту "я тут
  стою", а прицільно на конкретне місце.

Власні чекіни господаря профілю виключені з перевірки (стрічка
`get_my_friend_feed` показує і їх — сповіщати самого себе про власний
чекін нема сенсу).

**Реальне обмеження, не тимчасове**: `get_my_friend_feed` — це "checkin/
recent", за визначенням самого Untappd **лише друзі** підключеного
акаунта. Побачити чекін **будь-кого** в локації (не тільки друзів) цей
інструмент структурно не може. Для цього потрібен інший ендпоінт — реальний
Untappd має публічну стрічку конкретного місця (`GET /v4/venue/checkins/
{venue_id}`, не прив'язана до дружби); запит на цю фічу вже надіслано
мейнтейнеру MCP-сервера, відповідь очікується. Його додавання ще й змінить
механіку завдання локації: такий ендпоінт вимагає конкретний Untappd
`venue_id`, а не довільні GPS-координати + радіус, як зараз.

**Свідоме обмеження v1**: перевірка на новинки відбувається лише тоді, коли
фоновий цикл `_auto_toast_loop` реально опитує стрічку — тобто лише поки в
auto-тості є хоч одна активна ціль і він не на паузі. Це не окремий
цикл опитування — навмисно, щоб не витрачати додаткову квоту на ще один
незалежний поллінг; якщо колись знадобиться стеження без auto-тосту
взагалі, доведеться або завести окремий (платний квотою) цикл, або завжди
тримати auto-тост увімкненим хоча б з однією ціллю.

Відстань рахується формулою гаверсинуса (`festival_watch.haversine_meters`)
— чиста математика, без зовнішніх викликів.

**`/comment_watch`** (`comment_watch.py`) — сповіщає, коли хтось коментує
твій **власний** чекін, з кнопкою "💬 Відповісти" прямо в Telegram.
Відповідь публікується як `@юзернейм, <твій текст>` (у Untappd нема
справжнього тредингу коментарів, це найближчий видимий еквівалент "реплаю
конкретній людині"). Свій власний коментар до власного чекіну не
породжує сповіщення собі.

```
/comment_watch      - показати статус
/comment_watch on
/comment_watch off
```

**На відміну від auto-тосту й festival_watch, ця фіча НЕ може безкоштовно
"їхати зайцем" на спільній стрічці `get_my_friend_feed`.** Причина:
auto-тост/festival_watch дивляться лише на **нові чекіни** (усе, що
з'явилось після збереженого курсора) — обробили раз і більше не
повертаються. А коментар зазвичай приходить **пізніше**, вже після того,
як сам чекін давно "проїхав" повз той курсор, — тобто той спосіб, яким
інші фічі бачать усе безкоштовно, тут просто не спрацює, коментар
пропущено назавжди. Тому `_comment_watch_loop` — окремий, свідомо
недорогий цикл: раз на ~2 хв (`COMMENT_WATCH_INTERVAL_SECONDS`) по одному
запиту `get_user_checkins` **на власний юзернейм** на кожного власника з
увімкненим стеженням (не 75 запитів, як старий auto-тост до фікса — лише
1, бо "ціль" тут завжди одна: свої ж чекіни), перевіряє останні
`COMMENT_WATCH_CHECK_LIMIT` (10) чекінів на нові `comment_id`. Перший
тік після увімкнення нічого не сповіщає — лише запам'ятовує вже наявні
коментарі як базову лінію (той самий принцип "не сповіщати заднім числом",
що й в auto-тості/festival_watch).

Через 64-байтний ліміт Telegram на `callback_data` юзернейм коментатора не
влазить у саму кнопку разом із `checkin_id` — зберігається окремо в
`context.bot_data` (той самий підхід, що вже використовується для
`beer:{bid}` у пошуку), а кнопка несе лише `checkin_id`.

**Живою перевіркою знайдено баг**: і тут, і в сповіщенні `festival_watch`
текст спочатку писався звичайним рядком із `@юзернейм` без жодного
форматування — але сам Telegram-клієнт автоматично перетворює будь-яке
`@щось` у повідомленні на посилання на **Telegram-акаунт** із таким
юзернеймом (якщо такий існує), навіть без розмітки з нашого боку. У
результаті кнопка вела на випадковий чужий Telegram-профіль замість
реального Untappd. Виправлено: обидва сповіщення тепер шлють `parse_mode="HTML"`
з явним посиланням `<a href="https://untappd.com/user/{юзернейм}">` — і
все, що з зовнішнього джерела (ім'я пива, текст коментаря, юзернейми),
екранується через `html.escape` перед вставкою в розмітку.

**Нативний клікабельний @mention у самому коментарі Untappd — недосяжний.**
Untappd у своєму застосунку показує згадку користувача як
`<a href="/user/username">Ім'я</a>` прямо в тексті коментаря. Досліджено й
остаточно закрито: сирий `comment` із публічного API повертає **звичайний
текст без жодної розмітки** (`"Vitalii V. 🦭"`) — посилання рендериться з
приватних метаданих композера, яких API не віддає. Живою перевіркою
(3 реальні тестові коментарі через `comment_checkin`) підтверджено, що й
жоден текстовий обхід не працює: ні голий URL (`https://untappd.com/user/...`),
ні markdown-синтаксис (`[ім'я](url)`), ні bbcode (`[url=...]ім'я[/url]`) —
Untappd не автолінкіфікує жоден з них, усі рендеряться як сирий текст.
Ін'єкцію сирого HTML (`<a href=...>`) як текст коментаря — щоб перевірити,
чи екранує Untappd розмітку — свідомо не тестували: це означало б
пробувати вразливість (stored XSS) на чужій продакшн-системі без дозволу.
Тому формат відповіді бота (`@юзернейм, текст`) лишається як є: юзернейм
клікабельний лише всередині самого Telegram-сповіщення бота (через
`<a href="https://untappd.com/user/...">`), але не в самому коментарі на
Untappd.

**Сповіщати про згадку `@мене` під чиїмось чужим чекіном — теж
недосяжно, тим самим способом закрито.** Ідея: розширити `comment_watch`
за межі "коментар під МОЇМ чекіном" на "будь-де мене згадали" (наприклад
через спільну стрічку друзів, яку й так вже полить auto-тост). Живою
перевіркою того самого чекіна (`checkin_id 1600718664`) підтверджено:
нативна згадка через тап-підказку в застосунку (`comment_id 89598352`,
"Vitalii V. 🦭") не містить у сирому API-об'єкті **жодного** маркера —
ні `@`, ні окремого поля на кшталт `mentions`/`tagged_users`, взагалі
нічого, за що можна було б програмно зачепитись. Виявити можна тільки
той рідкісний випадок, коли хтось **вручну надрукував** `@юзернейм` як
буквальний текст (як-от наші власні відповіді через бот, `comment_id
89597864`: `"@ozerova, ❤️"`) — а це занадто дірявий фільтр, щоб на нього
покладатись як на реальну фічу сповіщень: більшість людей тегають через
тап-підказку, а не ручний ввід. Тому не реалізовано.

У сповіщенні `festival_watch` **пиво, пивоварня й локація теж стали
клікабельними** — `<a href="https://untappd.com/beer/{bid}">`,
`.../brewery/{breweryId}`, `.../venue/{venueId}` — усі id вже присутні в
тому самому фетчі стрічки, без жодного додаткового запиту. Спільний
хелпер `_html_link(url, text)` екранує текст перед вставкою; `url`
завжди будується самим кодом із числового id, ніколи із зовнішнього
рядка, тож сам не потребує екранування.

**Верхня панель Mini App** — два ряди: зверху ⚙️ (швидкі налаштування),
🔔 (останні події) і квота, знизу — таби (Черга/Прогрес/Авто-тост/Новинки/Бейджі)
на всю ширину з горизонтальною прокруткою (`overflow-x: auto`), щоб нові
вкладки не ламали розкладку, а прокручувались. Живою перевіркою знайдено
й виправлено класичну пастку флексбоксу: `.topbar-buttons` — елемент
колонки (`.topbar { flex-direction: column }`) і без явного `min-width: 0`
не стискався нижче ширини вмісту, через що **вся сторінка** розтягувалась
замість того, щоб рядок табів прокручувався сам у своїх межах.

- **⚙️ Налаштування** (`screen-settings`) — три перемикачі в одному місці
  (auto-тост / festival watch / comment watch), що читають і пишуть уже
  наявні статуси/тогл-роути кожної фічі напряму — сам екран не володіє
  жодним станом.
- **🔔 Останні події** (`screen-events`, `event_log.py`) — короткий
  журнал (до 50 записів на власника) того, що реально відбулось: тости,
  коментарі, новинки фестивалю. Пишеться в момент самої дії у фонових
  циклах (`_auto_toast_loop`, `_notify_new_comment`,
  `_check_festival_novelty`) — суто локальний запис, без додаткової
  квоти; читання теж локальне (`/api/checkin/events/get`).

  Кожен запис несе `beerId`/`checkinId`/`username`, тож рядок може бути
  інтерактивним: кнопка "🔗" відкриває пиво на Untappd (`openUntappdBeer`,
  той самий механізм, що й скрізь у застосунку), а для подій типу
  `comment` — кнопка "💬" розгортає інлайн-поле відповіді прямо на цьому
  екрані (`/api/checkin/events/reply` → `untappd_mcp.comment_checkin`,
  той самий `"@юзернейм, текст"` формат, що й відповідь через бота) — не
  треба переходити в чат із ботом, щоб відповісти на щойно побачений
  коментар. Для подій типу `toast` є кнопка "✕" — прибрати цю людину зі
  списку auto-тосту одним тапом (`/api/checkin/autotoast/remove_target`),
  без відкриття повного екрана з чекбоксами.

  **Непрочитане на 🔔.** Червона крапка (`.icon-btn.has-unread`)
  з'являється, коли є події новіші за останній перегляд — момент
  останнього перегляду зберігається в `localStorage` (`checkinHelper.
  lastSeenEventsAt`), суто на стороні клієнта: це персональна зручність
  одного переглядача, не дані, які треба синхронізувати між пристроями чи
  людьми, тож немає сенсу тягнути це на бекенд.

**🏅 Прогрес бейджів** (`screen-badges`, `badge_stats.py`) — реальний
прогрес до 133 справжніх бейджів Untappd (82 за стилем пива, 51 за
країною броварні), рахований локально з уже синхронізованої історії
`had_it_index` — жодного додаткового запиту до Untappd. Став можливим
без жодної нової витрати квоти саме завдяки тому, що стиль/пивоварня/
країна кожного пива вже й так зберігались у `had_it_index` (див. вище) —
бракувало тільки самого каталогу "які бейджі за що дають" і порогів.

Каталог (`badge_beer_categories.json`) зібраний вручну цього сеансу з
публічного https://badges.untappd.com/ (304 активних бейджі, з них 140+
відкрито індивідуально) — той самий підхід і формат цитування, що й
раніше для `badge_venue_categories.json`. Свідомо виключено все, що не
зводиться до "N різних пив стилю X" чи "N пив із країни Y": пороги по
IBU/ABV, тарний посуд (Bottle/Draft/Can/...), генерик-бейджі різноманіття
(Wheel of Styles, Beer Connoisseur), бейджі під конкретний список
броварень і одноразові special-edition/фестивальні бейджі, прив'язані до
конкретної названої пива, а не стилю.

Більшість бейджів — "type_pack", що левелюється безкінечно (до 100
рівнів каталогу): рівень 1 потребує `count` різних кваліфікуючих пив,
кожен наступний рівень — ще `count`. Виняток — 8 "Super Style: ..."
бейджів (доступні лише з підпискою Untappd Insiders): рівень 1 дає вже
**перше** таке пиво, і лише кожні наступні 5 підвищують рівень далі
(`first_level_count` окремим полем у каталозі). Стильний збіг —
підрядковий (наприклад бейдж "2X" зі стилем `"Imperial / Double"`
рахує будь-яке пиво, чия назва стилю **містить** цей підрядок — і
`IPA - Imperial / Double`, і `Stout - Imperial / Double`), країновий —
точний (бейдж або список країн реального регіону, наприклад "Central
America" + "South America" для регіональних бейджів).

**Super Style — показуються тільки підписникам Insiders, персонально.**
Спершу ці 8 бейджів просто виключались зі списку для всіх — але акаунт
власника бота не єдиний, хто ним користується, і хтось інший цілком може
мати активну підписку. Untappd сам віддає прапорець `is_supporter` прямо
в об'єкті користувача — і в `get_my_profile` (при `/connect_untappd`), і
в `.user` кожного чекіна з `get_user_checkins` (venue-бекфіл вже й так
його забирає щотижня, тож статус не застигає назавжди на моменті
підключення — оновлюється безкоштовно з того самого запиту). Кешується
в `untappd_tokens.json`; `badge_stats.compute_progress(beers,
is_supporter=...)` показує ці 8 бейджів лише тим, у кого прапорець
`True`.

**Прогрес-бар рахує позицію в межах поточного рівня, не кумулятивно.**
Перша версія рахувала `current / nextThreshold` від нуля — на високому
рівні (наприклад рівень 71 з кроком 5) шкала виглядала майже повністю
заповненою завжди (359 зі 360 потрібних сумарно), навіть щойно
розпочавши новий п'ятірковий крок. Виправлено: `_tier()` тепер рахує
`level_start` (скільки вже назбирано на старті поточного рівня), і
прогрес-бар показує `(current - level_start) / (nextThreshold -
level_start)` — тобто дійсні "4 з 5" всередині рівня, а не оманливі 99%.

**Venue-бейджі (за категорією локації) — той самий підхід, друга
хвиля.** `badge_venue_categories.json` спершу мав тільки категорії й
іконки (робився раніше для іншої мети — фільтра "🏅 Лише для бейджа" в
пошуку локацій), без порогів `count`/`levels` — тому спершу в списку
прогресу їх просто не було. Окреме дослідження додало ці поля всім 44
записам (той самий підхід, що й для пивних бейджів, без зміни решти
файлу) — 42 з них звичайні "type_pack" (5 нових локацій за рівень, до
100 рівнів), а 2 (**Brew Crawl** — 3 різні бари за одну ніч; **Last
Call** — 3 пива після 1-ї ночі в п'ятницю/суботу в одній локації)
виявились **прив'язаними до конкретного моменту/ночі**, а не до
довічного набору відвіданих локацій. Прогрес рахується з **нових**
даних: `venue_index.py` тепер зберігає категорію Foursquare кожної
відвіданої локації (безкоштовно, з того самого вже оплаченого
`get_user_checkins`, яким venue-бекфіл і так наповнює `venue_index.json`)
— і рахує **унікальні локації**, що збігаються з категоріями бейджа, а
не чекіни (повторний чекін в тій самій броварні не додає прогресу
вдруге). Саме тому Brew Crawl/Last Call свідомо виключені зі списку
(`badge_stats._VENUE_BADGES_NOT_COMPUTABLE`) — довічний лічильник
відвіданих барів показав би оманливий прогрес до бейджа, який
насправді вимагає "3 бари за одну ніч", а такої погодинної деталізації
`venue_index.py` не зберігає (і не повинен заради цих двох винятків).
Стара історія локацій (без категорії) підхопиться природним ресинком,
як і решта таких полів.

Бекенд віддає список у дефолтному порядку (найвищий `level`, далі `pct` —
спадання), але сам екран дає три режими сортування пілюлями (100→0 / 0→100
/ за алфавітом) і пошук — все клієнтське, без повторного фетчу: список
~170 бейджів приходить один раз при відкритті екрана й далі просто
пересортовується/фільтрується в браузері (`sortedBadges()`/
`renderBadgesList()` в `app.js`).

**Пошук працює й за тегами, не лише назвою.** Назва бейджа рідко натякає,
чим саме він заробляється ("Zwickel City" нічого не каже про
Kellerbier) — тому кожен рядок від бекенду тепер несе ще `kind`
(`style`/`country`/`venue`) і `tags` (сам список стилів/країн/категорій
локації з каталогу), і `badgeMatchesQuery()` в `app.js` шукає підрядок і
в назві, і в тегах — пошук "France" чи "IPA" знаходить усі бейджі, де
це реально фігурує в критерії, а не тільки в назві.

**Деталі бейджа (`screen-badge-detail`)** — тап по рядку відкриває
картку з великою іконкою, поточним прогресом, списком тегів-критеріїв
(`.badge-tag`) і текстом "скільки ще треба" (`countPerLevel` з бекенду).
Кнопка "🔗 Відкрити бейдж на Untappd" веде на публічну сторінку бейджа
(`badges.untappd.com/{id}-{slug}`) — але лише коли в каталозі вже є
поле `url` для цього бейджа (`badge.get("url")`, `None` — "ще не
досліджено", а не "не існує"); без нього кнопка просто не показується,
замість вести на здогадану й, можливо, хибну адресу. Дослідження всіх
177 URL (82+51+44 бейджі з трьох каталогів) — окрема фонова задача, що
не змінює жодне інше поле цих файлів.

**Відкрити бейдж прямо в застосунку Untappd, не в браузері.** Перша
спроба (`untappd://badge/{id}` як експериментальна кастомна URL-схема з
відкатом на веб) на практиці видавала помилку — власна схема Untappd
підтверджена лише для `beer/###`/`brewery/###`/`checkin/###`, жодного
шляху саме для бейджів не існує. Правильний формат виявився іншим:
`https://untappd.com/user/{юзернейм}/badges/{user_badge_id}` — це
**особисте посилання на конкретно ОТРИМАНИЙ екземпляр бейджа** (те саме,
що Untappd сам генерує при "поділитись бейджем"), на домені
`untappd.com`, який підтверджено віддає керування застосунку. На відміну
від generic-сторінки каталогу `badges.untappd.com/{id}-{slug}`, тут
немає жодної прив'язки до конкретного користувача.

`user_badge_id` з'являється лише в масиві `badges` конкретного чекіну, в
момент нагородження — немає окремого "покажи мої бейджі" ендпоінта. Новий
модуль `badge_index.py` дозбирає ці пари `{назва бейджа: user_badge_id}`
безкоштовно з того самого venue-бекфілу (`get_user_checkins` уже й так
повертає `badges.items` для кожного чекіну, де щось нагороджувалось) —
той самий принцип "captured for free", що й для стилю/країни/категорії
локації. `badge_name` в цих даних несе суфікс `"(Level N)"` для
бейджів, що левелюються — обрізається перед збереженням, щоб збігатися з
канонічною назвою в наших каталогах. `handle_badges_get` підставляє
`personalUrl` в кожен рядок, коли цей конкретний бейдж уже "засвітився"
в історії чекінів; доки ні — кнопка веде на generic-сторінку каталогу,
як і раніше (`b.personalUrl || b.url` в `app.js`).

**Кожен `user_badge_id` — застигла картинка на момент нагородження, не
поточний стан.** Перша версія зберігала перший знайдений екземпляр
назавжди ("перший не гірший за будь-який інший") — але живою перевіркою
підтверджено: сторінка старого екземпляра показує рівень, яким він БУВ
на момент нагородження, а не поточний прогрес акаунта. При перериваному
рестартами/квотою зворотному обході історії "перший знайдений" міг
виявитись давно застарілим рівнем (бейдж на 100, а посилання показує
рівень 56). Виправлено: `badge_index.record()` тепер парсить номер
рівня з суфікса `"(Level N)"` і залишає **найвищий** знайдений, ніколи
не регресує назад до нижчого — `_parse()`/порівняння `level >
existing_level` перед перезаписом.

**"Рівні не збігаються з реальним Untappd" — виявився реальним багом
захоплення даних, не "Untappd просто не має стилю".** Початкове
пояснення (мовляв, старі/рідкісні пива не мають `style` на боці
Untappd) виявилось хибним і спростоване живою перевіркою: пиво "Velvet"
(bid 6801282), що висіло без `style` навіть у вже `fully_synced`
акаунта, насправді має `beer_style: "IPA - Quadruple"` — підтверджено
прямим запитом `get_beer(6801282)`.

Справжня причина: `had_it_index`'s бекфіл ходить по `get_user_beers`
через **числовий offset**, а цей список сортується за `date`
(схоже, за датою **останнього** чекіну, а не першого знайомства, на
відміну від його ж date-фільтра — див. нижче). Повторний чекін уже
відомого пива підіймає його на позицію 0, зсуваючи все інше на одну
позицію — класична пастка offset-пагінації на списку, що
переупорядковується під час обходу: запис може "проскочити" повз
офсет, який walker уже пройшов **цього ж проходу**, і так — стабільно,
з ресинку в ресинк, для акаунта, що активно передегустовує вже випите.

Виправлено без переписування `had_it_index`'s основного механізму:
`had_it_index.enrich_from_checkin()` дозбирає відсутні `style`/
`brewery`/`country` (ніколи не чіпає `rating` — це значення конкретного
чекіну, а не агрегат з `get_user_beers`, і ніколи не створює новий
запис для невідомого `beer_id`) з того самого вже оплаченого
venue-бекфілу (`get_user_checkins`, курсор `maxId`) — того самого, яким
`venue_index.py` вже успішно ходить без цієї проблеми, бо `checkin_id`
монотонно спадний і байдужий до переупорядкувань. Нуль додаткової
квоти — просто ще один прохід по тій самій уже отриманій сторінці.

**Розбіжність назв стилів у `badge_beer_categories.json` — звірено проти
306 реальних стилів (з двох акаунтів, 53k+ чекінів), 15 виправлень, 4
з них потім відкочено.** Дослідник каталогу брав назви стилів із тексту
"як заробити" на сторінках бейджів, а не з реального рядка стилю
Untappd (`"Категорія - Підкатегорія"`) — конкретний приклад: "You Don't
Know Brett!" мав `"American Wild Ale"` замість реального `"Wild Ale -
American"`, через що 114 кваліфікуючих пив просто не рахувались.
11 виправлень мають тверде підтвердження (точне переставлення тих самих
слів, або системний патерн, підтверджений 15+ реальними записами —
наприклад усі `"Non-Alcoholic - X"` без слова "Beer"). Ще 4 — "Hella
Delicious!", "Old is New", "Oat of this World!", "Zwickel City" — були
здогадками за аналогією без такого підтвердження; одну з них ("Hella
Delicious!") спростувала жива перевірка (реальний `badge_description`
з чекіну прямо підтвердив, що ОРИГІНАЛЬНЕ формулювання було правильним
— бейдж просто ще не мав жодного кваліфікуючого пива в акаунті), тож усі
4 відкочено назад, а не залишено неперевіреними. Обидві корекції записані
в `_note` файлу з датою.

**Третій, протилежний тип бага: не недо-, а перерахунок.** "Session
Life" показував рівень 93 замість реального 86 — підрядковий пошук
навмисно широкий для узагальнених категорій (`"Stout"`, `"Imperial /
Double"` — це коректно, бейдж мусить рахувати всі підваріанти), але
ламається, коли сам запис каталогу вже є **повною, конкретною** назвою
стилю (`"IPA - Session"`), а в Untappd є ще конкретніший **сусідній**
підстиль, що починається з тих самих слів (`"IPA - Session New England
/ Hazy"` — окремий, інший стиль, не варіант "session"). 40 таких пив
зайво рахувались. Виправлено без ламання навмисно широких випадків:
префікс `"="` у `styles[]` (наприклад `"=IPA - Session"`) тепер означає
**точний**, а не підрядковий збіг — `badge_stats._split_style_matchers()`/
`_style_matches()`. Додано до "Session Life" (підтверджено живими
даними) і всіх 5 бейджів `"Super Style: X"` (кожен за конструкцією
називає рівно один конкретний стиль, ніколи не узагальнену категорію —
високий рівень впевненості з самого патерну назви, а не здогад). Ще 3
бейджі мають той самий теоретичний ризик ("Fruits of Your Labor",
"To The Port", "Tripping on TIPAs"), але це звичайні (не Super Style)
бейджі, де широта/точність не випливає з назви — залишені підрядковими,
а не вгадані.

### 1. Клонуй репозиторій і перейди в папку

```bash
cd beer_bot
```

### 2. Встанови залежності

```bash
pip install -r requirements.txt
```

### 3. Скопіюй базу пива

Поклади `beers_cache.json` у ту саму папку що й `bot.py`.

### 4. Отримай токени

- **Telegram Bot Token**: створи бота через [@BotFather](https://t.me/BotFather) → `/newbot`
- **Anthropic API Key**: отримай на [console.anthropic.com](https://console.anthropic.com)

### 5. Встанови змінні оточення

```bash
export TELEGRAM_BOT_TOKEN="your_telegram_token_here"
export ANTHROPIC_API_KEY="your_anthropic_key_here"
```

Або створи файл `.env` і завантажуй через `python-dotenv`:
```
TELEGRAM_BOT_TOKEN=your_telegram_token_here
ANTHROPIC_API_KEY=your_anthropic_key_here
```

Для фестивального чекіну (`/checkin`) додатково потрібні:
```
UNTAPPD_MCP_URL=https://<адреса твого Untappd MCP-сервера>/mcp
PUBLIC_BASE_URL=<публічна HTTPS-адреса, де бот доступний — Fly.io URL або ngrok/cloudflared тунель для локального тесту>
CHECKIN_DRY_RUN=1

# опціонально — токен-фолбек лише для власника бота (щоб не проходити /connect_untappd самому)
UNTAPPD_MCP_TOKEN=<особистий bearer-токен власника>
OWNER_TELEGRAM_ID=<твій числовий Telegram user id>

# опціонально — вмикає "🧭 Локації поруч" (без нього кнопка просто не спрацює)
FOURSQUARE_API_KEY=<ключ з foursquare.com/developer, безкоштовний тариф>

# опціонально — який festival JSON вантажити (`bot.py`'s load_db()); за замовчуванням mbcc_beers.json
FESTIVAL_BEERS_FILE=mbcc_beers.json
```
Кожен інший користувач підключає свій акаунт командою `/connect_untappd` у боті — токен ніде в `.env` для них не потрібен.

Щоб перейти на новий фестиваль — поклади новий JSON поруч (той самий формат:
або `{"session": [beers...]}`, або плаский список), встанови
`FESTIVAL_BEERS_FILE=новий_фест.json` і перезапусти бота. Черга
(`checkin_queue.json`) при цьому **не** очищується автоматично — застарілі
пункти попереднього фестивалю просто стають нерелевантними; кнопка
"🗑 Очистити все" на екрані черги — спосіб прибрати їх вручну, для себе.
Без `UNTAPPD_MCP_URL`/`PUBLIC_BASE_URL` фіча просто вимикається (бот стартує
без веб-сервера, `/checkin` не з'являється в меню). `CHECKIN_DRY_RUN=1`
логує запит на чекін замість реального виклику Untappd — прибери цю змінну
(`fly secrets unset CHECKIN_DRY_RUN`), тільки коли переконаєшся, що все працює.

Telegram Mini App вимагає справжній HTTPS-URL — для локального запуску
`http://localhost:...` не підійде, телефон його не побачить. Піднімай тимчасовий
тунель (`ngrok http 8080` або `cloudflared tunnel --url http://localhost:8080`)
і став видану адресу в `PUBLIC_BASE_URL`.

### 6. Запусти бота

```bash
python bot.py
```

```ini
WorkingDirectory=/path/to/beer_bot
ExecStart=/usr/bin/python3 bot.py
Environment=TELEGRAM_BOT_TOKEN=xxx
```

```bash
tmux new -s beerbot

```

## Вартість

- Claude Vision (`claude-sonnet-4-5`): реально ~$0.013–0.015 за успішне фото, не $0.003 — у промпт на кожен запит вшивається повний `VISION_PROMPT` (~815 токенів) + список усіх броварень фестивалю (~300 токенів) + саме зображення (~2000 токенів)
- Плюс повтори: за логами, ~22% фото вимагають хоча б одного повторного платного виклику через обрив з'єднання (`VISION_MAX_ATTEMPTS=4`), а частина фото не розпізнається навіть після всіх спроб — це теж оплачені виклики без результату
- За 100 фото реалістично ≈ $1.5–2, не $0.30

## Обмеження

- Untappd не має публічного API, тому для пив поза базою (у фото-флоу) генерується посилання на Google пошук — фестивальний Mini App (`/checkin`) цього обмеження не має, там пошук іде напряму через Untappd MCP
- Якість розпізнавання залежить від освітлення і чіткості фото
